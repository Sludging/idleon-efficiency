## Player-facing information and navigation conventions

These are observed conventions/recommendations, not a Menagerie mockup or fixed layout.

- **Access / locked:** `app/account/tome/content.tsx:75-112` explicitly distinguishes globally locked feature from unlocked score and dims incomplete records; `app/world-7/legendTalents/content.tsx:63-89` keeps actual talent records visible with level/cap, effect, next-level detail, and reduced opacity when unowned. Applicable information: access versus progress, and locked state distinct from completion. Do not copy Tome's exact lock gate or legacy opacity as universal behavior.
- **Overview / progression:** Tome shows total score and character source before its line collection (`tome/content.tsx:86-103`). Legend Talents presents account points/available summary before upgrade records (`legendTalents/content.tsx:29-64`). This supports a compact account overview followed by progression details where it helps players interpret state; it does not dictate tabs or hierarchy.
- **Bonus listings / detail disclosure:** Legend Talents shows owned level/cap and description in each card, with next level detail when applicable (`legendTalents/content.tsx:63-89`). Account Cards keeps collection identity visible and discloses collection/drop and star-level details in `TipDisplay` (`app/account/cards/content.tsx:25-90`). UI guide recommends all real locked/maxed entries by default, no filler, and useful detail that is not hover-only (`docs/agents/ui-patterns.md:103-110,123-127`). Use these only as evidence that status, effects, and selectively disclosed detail are established; do not prescribe cards, grids, columns, or specific fields for Menagerie.
- **Navigation and layout:** `docs/agents/ui-patterns.md:70-102,128-142` establishes ordinary page heading, shared account loading, selectors' ownership boundaries, app-provided page width, and backend/UI separation. `docs/insights/ui-feedback.md:3-18` favors dense readable information, local effect/progression relationships, verified icons, concise contextual explanations, and local navigation. There is no evidence here requiring new navigation or a specific tab scheme.
- **Freshness / profiles:** shared account loading and status belong to `appDataStore`/`DataStatusDisplay` (`docs/agents/ui-patterns.md:134-139`). Save-time elapsed displays use the save timestamp, not Zustand's `lastUpdated` refresh dependency (`ui-patterns.md:128-133`); `app/players/content.tsx:194-247` computes elapsed time from saved `lastUpdated`. Public profiles are an existing product capability (`app/profile/upload/content.tsx:95-109`), but the reviewed feature examples do not establish whether Menagerie appears in public profiles, nor a Menagerie freshness/last-import display convention. Recommended question: treat profile visibility as a product requirement to confirm; never imply live state from an imported snapshot. Do not invent freshness indicators or promise profile support absent approval/evidence.
- Rendered-example limit: UI patterns directs inspecting rendered examples for composition (`ui-patterns.md:17-35`), but this assignment forbids UI design. Existing retained Spelunking browser proofs are linked from its handoff (e.g. `docs/plans/spelunking-research-brief.md:36-39` and later evidence sections); they demonstrate actual feature UI, but no Menagerie rendering exists in inspected evidence. This is a gap, not a reason to design a preview here.

## Coarse scope recommendation and limits

At phase 1, frame player outcomes around understanding account Menagerie access/progression, mission requirements and progress, currencies/resources, unlock availability/ownership, and the effect of catalog bonuses—only where game evidence confirms these meanings and values. Keep character-specific, freshness, and public-profile behavior unresolved until save ownership and product precedent are verified. Treat the 33-versus-25 mission discrepancy and unmapped matrix as explicit evidence questions.

For phase 2, if brief approval occurs, group work only by complete player experiences supported by evidence; each proposed part should join trusted state/calculations to usable information. Keep integration of incoming bonus sources coherent and avoid duplicate effect work if parts are split. Do not expand into Menagerie side jellyfish, broad cross-domain integration, calculators/planning, or speculative mission-count assumptions: the existing v1.23 summary treats side jellyfish and shared bonus integration as separate candidate work (`v1.23-work-summary.md:32-80`). This recommendation does not decide whether those areas are included; the assigning session/human must select scope from approved outcomes.
